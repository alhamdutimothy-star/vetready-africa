## C. Migration 015

`015_competency_profile_snapshots.sql` adds one receipt table, owner index, canonical JSON/digest helpers, allowlisted-field/provenance/owner validation, append-only protection and an atomic minimal audit trigger. It is additive and forward-only. Migrations 001–014 and source tables are unchanged. Test fixtures verify upgrade from populated 014 and migration reruns without rewriting any pre-existing table contents.

Snapshot input is generated by the server, never accepted from callers. Candidate, source identities and ownership are linked to existing rows. Digests detect content mismatch; historical retrieval also reruns the retained engine and compares the exact result. A unique owner/command constraint and transaction retries make duplicate commands return one receipt and one audit event. Failed audit recording rolls back the receipt. Tests use only the existing dedicated local `_test` database; this task does not apply 015 to a production/development application database.

## D. Aggregation and evidence precedence

The engine reads the complete owner history within one repeatable-read transaction. Exact child versions and source versions remain distinct. Within each independent facet, supported verification precedes assessed, claimed and pending evidence; source recency then stable identifiers resolve ties. A newer unverified claim cannot replace existing supported verification. Revocation, supersession, withdrawal, rejection, requested revision and recorded expiry exclude a source before selection; history and reasons remain visible. Demo flags remain visible alongside lifecycle exclusions. No validity period is invented.

Knowledge/case verification uses existing canonical review and independent moderation records. Practical evidence from Phase 3F remains demo-only. Training completion is separate learning participation, never a claim or verification. Legacy group documents remain unconfigured group claims, never distributed to child competencies. Shared competency reuse preserves one source with its original pathway and explicitly states that other pathway context is unevaluated. A presentation-only highest verified facet is not a readiness or equivalence rule.

## E. Skills Passport privacy model

All six APIs require current candidate capability and resolve ownership from the authenticated principal. Reviewer/admin capability does not grant another candidate's profile or receipt. Every nested passport object is explicitly allowlisted; strict web response schemas reject additions. Passport fields include source IDs, versions, dates and dispositions, excluding narratives, private documents, reviewer identity, review/decision identifiers and content, moderation records, tokens and session information. Responses and authenticated pages are no-store. Public/employer sharing is disabled and has no route.

The UI distinguishes self-declared, document verified, knowledge assessed, case assessed and practically verified categories, plus simulation/workplace categories. A category heading never claims verification. Group claims and learning are separately explained. Competency/source history is paginated; aggregation has no UI list cap. Historical receipt pages explicitly warn that current evidence may have changed.
